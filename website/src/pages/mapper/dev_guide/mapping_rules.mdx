# Mapping rules

Mapping Rules determine how to link (and potentially modify) between `source_fields`
(input data) and `destination_fields` (output data) when building `CDM` objects.

## Prerequisites

Validation of `ScanReportConcept` occurs when they themselves are created. Their creation will fail if:

1. The associated `ScanReportTable` does not have a `person_id` marked.
1. The associated `ScanReportTable` does not have a `date_event` marked.

These are requirements for building the mapping rules

## Table roles

Each `ScanReportTable` has a `table_role`, set on its **Edit Table** page, which
changes how its rules are built:

| Role       | Rules built from its Concepts                                                                                                                                                         |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `standard` | As described below: each Concept's domain gives its `destination_table`.                                                                                                              |
| `death`    | Concepts are recognised as causes of death in the `death` table, and the Date Event maps to its death date.                                                                          |
| `note`     | None, except for value-mapped fields (below). Each row is a `note` record, built from the table's field mappings.                                                                    |
| `note_nlp` | Each Concept gives `note_nlp` rules (`nlp_datetime`, `note_nlp_concept_id`, `note_nlp_source_concept_id`), plus the usual rules in its domain's table if the domain has one.         |

`ScanReportTable.type_concept` (optional) is written to the `*_type_concept_id`
field of every record built from the table, e.g. 32858 (NLP) for NLP-derived
records.

### Note and Note NLP tables

The fields of `note` and `note_nlp` records aren't mapping rules. They're stored
as `ScanReportTableFieldMapping`s, one per OMOP field, each filled from a source
column, with a constant, or (for concept fields) from the concepts mapped to a
column's values (`map_values`). A `note_nlp` table's `note_nlp_concept_id` can
instead name a vocabulary whose codes the column holds (`vocabulary_id`), for
Carrot Transform to look up.

A value-mapped field's Concepts give one rule each, for that field only, rather
than the rules described below. Concepts with ID 0 ("No matching concept") give
no rules.

NLP-derived record settings are stored in `NlpLinkSettings` (the optional
`fact_relationship` link concepts) and `NlpDerivedRecordExclusion` (source
column values that stop derived records).

These are exported only in the JSON V2 rules. See [V2 rules for notes and
NLP](/transform/rules_v2_notes_nlp).

## Building Rules

For each `ScanReportConcept` that is created, the procedure to build Mapping-Rules proceeds as follows:

1. The `destination_field` (`OmopField` object) of the `<domain>_concept_id` is found using `ScanReportConcept.concept.domain_id`. The `destination_table` is linked to the object.

1. From the `source_field` or `source_value` of the `ScanReportConcept.content_type` the `source_table` is found.

1. At least five common mapping rules are first created:

### 1. Person ID

Is created for the `destination_field` of the (already found) `destination_table`:

- Every `CDM` object contains a `person_id`
- The rule is built with the current `source_table` and `source_value` or `source_field`, as well as with the `concept`, linking it to the `destination_table`.

### 2. Date Events

At least one date based `destination_field` of the associated `destination_table` is created:

- Every `CDM` object must contain at least one `date_event`
- They are determined by the global variable `m_date_field_mapper` which is defined in `services_rules.py`:

```python
m_date_field_mapper = {
    'person': ['birth_datetime'],
    'condition_occurrence': ['condition_start_datetime','condition_end_datetime'],
    'measurement':['measurement_datetime'],
    'observation':['observation_datetime']
}
```

- As can be seen, most CDM objects have one date event, however `condition_occurrence` is an example where two date events are/were needed

### 3. Source Value

- A rule is created by finding the `<domain>_source_value` (`OmopField`) for the current `destination_table`. As with previous rules, the rule links this with the `concept` and the `source_table` and `source_field`.

<Callout>
  This rule could be duplicated for the `destination_field` called
  `value_as_number` (or `value_as_float`). This appears in `measurement` and is
  a clone of `source_value`, with a different output format (FLOAT instead of
  CHAR). Formatting of rules is handled by the ETL-Tool, and therefore from the
  mapping-pipeline point of view, these rules are the same.
</Callout>

### 4. Concept ID

- A rule is created by finding the `<domain>_concept_id` (`OmopField`) for the current `destination_table`. As with previous rules, the rule links this with the `concept` and the `source_table` and `source_field`.

### 5. Source Concept ID

- A rule is created by finding the `<domain>_source_concept_id` (`OmopField`) for the current `destination_table`. The rule links it with the `ScanReportConcept`'s source concept, and with the `source_table` and `source_field`.

`ScanReportConcept.source_concept` records the concept the value's code was found as in its source vocabulary, before following "Maps to" to the standard concept (`ScanReportConcept.concept`):

- **Vocabulary (V) concepts** from a data dictionary store both: the source concept is `concept_id_1` of the "Maps to" relationship and the standard concept is `concept_id_2`. Source concepts may be non-standard. When the code is already a standard concept it maps to itself, so both are the same.
- **Manually added (M) concepts** have no source vocabulary, so `source_concept` is empty and `<domain>_source_concept_id` is the mapped concept.
- **Reused (R) concepts** carry over the source concept of the concept they were reused from, if it has one.

All rules exports write the source concept to `<domain>_source_concept_id`, falling back to the mapped concept when it's empty. Re-running auto-mapping fills it in on existing V concepts.

## Downloading Rules

In `services_rules.py` the function

```python
def get_mapping_rules_json(qs:QuerySet) -> dict:
```

builds a dictionary that is converted to a `json` format before it is downloaded when the "Download Mapping Rules" button is clicked.

The function works as follows:
Given a query set of all `MappingRule`s associated to a given `ScanReport`:

1.  Group them based on the associated ScanReportConcept (object that spawned them)
1.  Create a dictionary to contain each destination_table
1.  Loop over all rules associated to each ScanReportConcept (>=5 rules)
1.  Retrieve the source_table, source_field, destination_field from the `MappingRule`
1.  If the `destination_field` is a `concept_id` add "Term Mapping" to the output json. Add this as
    map or a scalar, depending on if it’s a ScanReportValue or ScanReportField that is to be mapped

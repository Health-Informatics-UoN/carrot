# V2 rules for notes and NLP

Carrot Mapper's **Mapping JSON V2** rules describe, for each OMOP table and each
source table, how records are built:

```json
{
  "cdm": {
    "<omop_table>": {
      "<source_table>.csv": {
        "person_id_mapping": { "source_field": "...", "dest_field": "person_id" },
        "date_mapping": { "source_field": "...", "dest_field": ["..._datetime"] },
        "concept_mappings": {
          "<source_field>": {
            "<value>": { "<dest_field>": [concept_id] },
            "original_value": ["..."]
          }
        }
      }
    }
  }
}
```

By default one record is built for every concept a mapped source value maps to,
and the only source value copied into a record is the mapped column's own value.
That can't describe tables such as `note` and `note_nlp`, whose records:

- are one per source row, with no concept mapping driving them (`note`)
- copy several other columns into each record (`note_text`, `lexical_variant`, ...)
- carry fixed values (`nlp_system`, type concepts)
- link to records in another table (`note_nlp.note_id` to `note.note_id`)

The optional keys below cover these cases. Carrot Mapper writes them for tables
set up as described in [Mapping notes and NLP
output](/mapper/user_guide/notes_and_nlp). Each key applies to every record built
from its source table's block, and all of them can be combined with the keys
above. Rules that don't use them are transformed as before.

<Callout type="info">
  The `note` and `note_nlp` tables are part of OMOP CDM v5.4, so run Carrot
  Transform with `--omop-ddl-file @carrot/config/OMOPCDM_postgresql_5.4_ddl.sql`.
  The default DDL is CDM v5.3.
</Callout>

## `field_mappings`

Copies another source column into a destination field.

```json
"field_mappings": { "note_text": "text", "note_title": "title" }
```

## `constant_mappings`

Writes the same value into a destination field on every record.

```json
"constant_mappings": { "note_type_concept_id": 32817, "nlp_system": "MedCAT 1.12" }
```

## `value_mappings`

Fills a concept field with the concept a source column's value maps to, such as
a note's class from its type. Each value is mapped to a concept in Carrot Mapper,
as for any other field.

```json
"value_mappings": {
  "note_class_concept_id": {
    "source_field": "note_type",
    "values": { "Outpatient note": 706556, "Discharge summary": 706531 }
  }
}
```

Unlike `concept_mappings`, this doesn't create records: it fills one field of
each record the block builds. Values that aren't listed (or are empty) leave the
field at its default, which is 0 ("no matching concept") for required concept
fields. How many records had a value with no concept is reported per table at
the end of the run.

## `record_key`

Registers each written record's generated ID (its auto-numbered field, e.g.
`note_id`) under the value of a source column, so that other tables can refer to
it. Keys are held per OMOP table, so they must be unique across all source tables
feeding that OMOP table.

```json
"record_key": { "source_field": "note_ref" }
```

## `references`

Fills a destination field with the generated ID of a record in another OMOP
table, looked up by the value of a source column against that table's
`record_key`s. A record whose reference can't be resolved isn't written; the
number of such records per table is logged as a warning at the end of the run.

```json
"references": { "note_id": { "table": "note", "source_field": "note_ref" } }
```

Source tables whose blocks define `record_key`s are processed before source
tables whose blocks reference them.

## `derived_from`

Marks the records of a block as derived from the records another table gets
from the same source row, such as conditions derived from NLP output
(`note_nlp`). The source table must also have a block for that table.

```json
"derived_from": {
  "table": "note_nlp",
  "exclude_values": { "negated": ["true", "1"], "subject": ["family"] },
  "fact_relationship": {
    "domain_concept_id": 1111111,
    "source_domain_concept_id": 2222222,
    "relationship_concept_id": 3333333,
    "reverse_relationship_concept_id": 4444444
  }
}
```

- A derived record is only written if its source row produced at least one
  record in `table`. If it didn't (for example the note_nlp record's note wasn't
  found), the derived record is skipped.
- `exclude_values` (optional) maps source columns to values that stop derived
  records for a row, such as negated or family-history terms. Values are compared
  ignoring case and surrounding spaces. The row's record in `table` is still
  written.
- `fact_relationship` (optional) links each derived record to the record it came
  from, as two `fact_relationship` rows, one in each direction, following the CDM
  convention. A derived record is linked to the row's records with a matching
  concept (e.g. `note_nlp_concept_id` equal to `condition_concept_id`), or to all
  of the row's records in `table` if none match. `domain_concept_id` is the
  domain of the derived record and `source_domain_concept_id` the domain of the
  record it came from. The IDs above are placeholders: the standard vocabularies
  don't yet have concepts for these links, so Carrot Mapper only writes this key
  when they're set.

For each source row, the tables records are derived from are written before the
tables derived from them. Skipped derived records are reported per table at the
end of the run, and aren't counted as rejected rows.

## Records without concept mappings

A block with no `concept_mappings` (or an empty one) that uses any of the keys
above builds exactly one record per source row, from `person_id_mapping`,
`date_mapping` and those keys. A block with `concept_mappings` builds records
exactly as before, and the keys above are applied to each of them. A block with
neither builds nothing, as before.

`note_nlp` has no `person_id`, so a source table that only feeds `note_nlp` needs
no `person_id_mapping`.

## Example

The concept IDs below are illustrative; check them against your vocabulary.

```json
"note": {
  "notes.csv": {
    "person_id_mapping": { "source_field": "patient_id", "dest_field": "person_id" },
    "date_mapping": { "source_field": "note_date", "dest_field": ["note_datetime"] },
    "record_key": { "source_field": "note_ref" },
    "field_mappings": { "note_text": "text", "note_title": "title" },
    "constant_mappings": {
      "note_type_concept_id": 32817,
      "encoding_concept_id": 32678,
      "language_concept_id": 4180186
    },
    "value_mappings": {
      "note_class_concept_id": {
        "source_field": "note_type",
        "values": { "Discharge summary": 706531 }
      }
    }
  }
},
"note_nlp": {
  "nlp.csv": {
    "date_mapping": { "source_field": "note_date", "dest_field": ["nlp_datetime"] },
    "references": { "note_id": { "table": "note", "source_field": "note_ref" } },
    "field_mappings": { "lexical_variant": "term", "snippet": "snippet", "offset": "term_offset" },
    "constant_mappings": { "nlp_system": "MedCAT 1.12" },
    "concept_mappings": {
      "snomed_code": {
        "22298006": { "note_nlp_concept_id": [4329847], "note_nlp_source_concept_id": [4329847] },
        "original_value": []
      }
    }
  }
},
"condition_occurrence": {
  "nlp.csv": {
    "person_id_mapping": { "source_field": "patient_id", "dest_field": "person_id" },
    "date_mapping": {
      "source_field": "note_date",
      "dest_field": ["condition_start_datetime", "condition_end_datetime"]
    },
    "concept_mappings": {
      "snomed_code": {
        "22298006": { "condition_concept_id": [4329847], "condition_source_concept_id": [4329847] },
        "original_value": ["condition_source_value"]
      }
    },
    "constant_mappings": { "condition_type_concept_id": 32858 },
    "derived_from": { "table": "note_nlp", "exclude_values": { "negated": ["true"] } }
  }
}
```

## Not yet supported: `code_lookup`

For an NLP table whose `note_nlp_concept_id` is set to **Codes from a vocabulary**
in Carrot Mapper, the `note_nlp` block also has a `code_lookup` key, naming the
column holding the codes and their vocabulary. Carrot Transform doesn't support
it yet: it ignores the key, so those `note_nlp` records have no concepts and no
records are derived from them. Until it's supported, use **Map column values**
for `note_nlp_concept_id`.
